# ADR-0003: Storage driver and encryption by default

- **Status:** Accepted (Phase 1, 2026-10-17), subject to the owner's Phase 1 approval
- **Deciders:** project owner (approval), implementation (evidence)
- **Related:** [SECURITY_MODEL.md §5.1](../SECURITY_MODEL.md), [TECHNOLOGY_DECISIONS.md §4](../TECHNOLOGY_DECISIONS.md), spikes SPK-04 and SPK-05 ([TECHNOLOGY_DECISIONS.md §10](../TECHNOLOGY_DECISIONS.md)), risk R23

## Context

LAZIS stores highly personal data in SQLite. The owner requires encrypted storage from the foundation phase, with no plaintext fallback. Later phases need two SQLite extensions in the same database: **FTS5** (full-text search) and **sqlite-vec** (vector KNN). Phase 0 left two questions open:

- **SPK-04:** which Python driver can load extensions (stdlib `sqlite3`, `sqlcipher3`, or `apsw`)?
- **SPK-05:** do FTS5 and sqlite-vec work under SQLCipher, and what does encryption cost for brute-force KNN over 50k × 768 vectors (target ≤ 30 ms, set for plaintext)? Where does the key live?

## Decision

1. **Driver: `sqlcipher3` 0.6.4** (official wheel with SQLCipher 4.19.0 community, SQLite 3.53.4, bundled OpenSSL 3.6.0). It is imported only in `core/src/lazis/storage/driver.py` (enforced by an import-linter contract). The stdlib `sqlite3` is never used for application data.
2. **Encryption by default, no fallback.** Every database and backup is SQLCipher with a raw 256-bit key (`PRAGMA key = "x'…'"`, no PBKDF2 needed for a random key). The app refuses to start if `PRAGMA cipher_version` is empty, refuses an existing plaintext file, and checks the on-disk header after opening.
3. **Key:** generated by the Rust shell with `SecRandomCopyBytes`, stored in the login Keychain (service `com.lazis.app`, account `database-key-v1`, not synchronizable), handed to the backend over stdin. Recovery code format `LZR1` ([SECURITY_MODEL.md §5.1](../SECURITY_MODEL.md)).
4. **Extensions** are loaded with `enable_load_extension(True)` → load → `enable_load_extension(False)`, so SQL cannot call `load_extension()`.
5. **Vector search under encryption (applies from P6):** the connection that serves KNN gets a page cache sized to the vector tables (`PRAGMA cache_size`, e.g. vector bytes × 1.1, capped by the memory budget) and is pre-warmed in the background after startup. int8 vectors with float rescoring are the fallback if the memory budget is tight. This choice is re-validated with the embedding model chosen in P2 (ADR-0002).

## Evidence (SPK-04 / SPK-05)

Machine: MacBook Pro M4 Pro, 24 GB, macOS 27.0.1, CPython 3.13.16. Script: `core/spikes/spk05_storage.py` (synthetic random data in a temporary directory; `make spike-storage` reproduces it). Raw results: `core/spikes/results/spk05-m4pro-2026-10-17.json`. Total run time 16.6 s.

**SPK-04 — compatibility**

| Check | Result |
|---|---|
| stdlib `sqlite3` (uv CPython) `enable_load_extension` + sqlite-vec | available, loads (v0.1.9) — but cannot encrypt |
| `sqlcipher3` + sqlite-vec | loads (v0.1.9) |
| FTS5 compiled in SQLCipher build | yes; create / insert / `MATCH` work |
| `SQLITE_OMIT_LOAD_EXTENSION` | not set |
| SQL `load_extension()` after disabling | refused |
| `apsw` needed | no |

**SPK-05 — vectors, 50,000 × 768, k = 10, 40 queries** (p50 / p95 in ms)

| Variant | File | Insert | 2 MB page cache (SQLite default) | 256 MB page cache |
|---|---|---|---|---|
| float32, plaintext (reference) | 155.5 MB | 1.0 s | 19.6 / 20.2 (first 20.2) | 19.7 / 20.3 (first 19.9) |
| float32, **encrypted** | 158.5 MB | 1.2 s | 160.1 / 162.3 (first 161.2) | **5.4 / 5.6** (first 165.2) |
| int8, **encrypted** | 40.5 MB | 0.4 s | 40.7 / 41.4 (first 41.2) | **2.4 / 2.4** (first 43.8) |

Interpretation:
- With the default cache every encrypted query decrypts the whole vector table (~160 ms) — this would miss the 30 ms target.
- With a cache that holds the vector pages, encrypted KNN is **faster than the plaintext reference** (5.4 ms vs 19.6 ms). The likely explanation (not separately verified): for the plaintext file SQLite reads large blobs directly from the file (direct overflow read, which bypasses the page cache), while the encrypted file must go through the pager, so its decrypted pages stay cached in memory.
- The price is memory (≈ the vector table size, ~160 MB for 50k float32 or ~40 MB for int8) and one cold query (~165 ms / ~44 ms) after opening, which a background pre-warm hides.

**SPK-05 — FTS5, 50,000 synthetic Turkish-like documents of 20–80 words** (p50 / p95 in ms, default cache)

| Variant | File | Insert | single term | two terms (OR) |
|---|---|---|---|---|
| plaintext | 37.6 MB | 0.42 s | 0.24 / 0.29 | 0.46 / 0.51 |
| encrypted | 39.6 MB | 0.44 s | 0.25 / 0.29 | 0.46 / 0.50 |

FTS5 cost of encryption: negligible.

**SPK-05 — Keychain item path:** creation, read-back, overwrite and deletion of a generic password through `security-framework` work from the shell (opt-in test `make test-keychain` on a dedicated test item; the real app flow was run with a throwaway profile and cleaned up). Ad-hoc signed development builds may trigger a one-time prompt after a rebuild because the item's ACL is bound to the code signature; Developer ID signing removes this (P15).

## Consequences

- The FileVault-only fallback in SECURITY_MODEL §5.1 is **not needed**; encryption stays on by default for every phase.
- P6 must implement cache sizing and pre-warm for the vector connection and include the cold-start query in its latency tests. The memory budget in P2's model decision should reserve room for the vector cache (~40–160 MB at 50k items, scaling linearly).
- The backend uses one connection on a dedicated thread, so the page cache is shared by all queries on it.
- Storage depends on the `sqlcipher3` wheel. If a future Python version lacks a wheel, building it from source needs OpenSSL headers — tracked as a packaging risk (R15). The wheel's bundled OpenSSL must be watched for security updates.

## Alternatives considered

- **stdlib `sqlite3` without encryption + FileVault only:** rejected; encryption at rest is a project requirement, and FileVault does not protect against other local users or a copied file while the machine is unlocked.
- **`apsw` with a SQLCipher build:** unnecessary; `sqlcipher3` works and keeps the DB-API interface.
- **Field-level encryption:** rejected; breaks FTS5 and vector search.
- **Separate plaintext vector index:** rejected; embeddings can leak content.

## Amendment 1 (Phase 1.1, 2026-10-17): crash-safe restore

**Problem found in review.** `restore_snapshot` (Phase 1) had four weaknesses:

- **WAL deleted before the replace.** It deleted the target's `-wal`/`-shm`/`-journal` *before* `os.replace`. If the replace then failed, the newest committed transactions, which may exist only in the WAL, were gone. A test now shows such data is absent from the main file alone.
- **No copy of the replaced database** was kept.
- **No durability:** there was no `fsync` of the copy or the directory.
- **No interlock or recovery:** nothing stopped a restore while a backend had the database open, and an interrupted restore had no recovery path.

**Decision.** The protocol in the module docstring of `core/src/lazis/storage/backup.py` and [SECURITY_MODEL.md §5.1](../SECURITY_MODEL.md):

1. The data-directory lock (now owned by `storage` and held for as long as a database is open).
2. Validation:
   - the manifest is required and its SHA-256 must match;
   - the snapshot must open with the key;
   - `quick_check` and `cipher_integrity_check` must pass;
   - the LAZIS schema must be present and not newer than the app.
3. A durable (`F_FULLFSYNC`) staged copy inside the data directory, re-verified.
4. The current files are *moved* (renamed) aside, never deleted.
5. Install and verify the staged copy.
6. **Commit point:** an atomic directory rename of the moved files to `backups/pre-restore-<stamp>/`; the last 3 are kept.

Errors before the commit roll back immediately. Crashes before the commit are rolled back by `recover_interrupted_restore`, which `open_storage` runs before opening anything; the state is inferred from which files exist, so recovery is idempotent. Snapshots also became stricter:

- a failed export leaves no partial file;
- the manifest is written atomically;
- labels are validated.

**Evidence** (`core/tests/integration/test_restore_safety.py`, synthetic data, 36 tests):

- Backup → restore yields a logically identical database: same row count and checksum for every table, including history and the audit log (SEC-05).
- The successful path keeps the replaced database *including its WAL* and reopens it with the newest value.
- Restore into an empty directory works.
- 8 kinds of bad backup and a wrong key are rejected with the database byte-for-byte unchanged. The 8 kinds:
  - random bytes;
  - a bit flip with the manifest unchanged;
  - a bit flip with the manifest rewritten (caught by the page HMAC);
  - a missing manifest;
  - a truncated file;
  - a plaintext SQLite file;
  - a non-LAZIS database;
  - a newer schema.
- Injected failures at 7 steps roll back to an identical original. The steps are:
  - ENOSPC while staging;
  - errors after staging;
  - EACCES/EIO while moving each file;
  - after install;
  - after verification.
- Real process exits (`os._exit`) at the same 7 steps are rolled back at the next start. A crash after the commit keeps the restored database.
- A really read-only data directory leaves the original intact, and the next start cleans up.
- A restore is refused while the database is open. Recovery is audited (`backup/restore_recovered`).

**Not covered** (documented in the Phase 1.1 report):

- A real power cut, which was not tested.
- The guarantee assumes the data directory is one local APFS volume, where `rename` is atomic.
- A restore UI does not exist yet; restore is a library function until P6.
